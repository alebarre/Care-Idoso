## Contexto

Atualmente a aplicação utiliza apenas um token JWT de acesso com duração longa. Para melhorar a segurança da autenticação stateless, vamos introduzir o fluxo de **Refresh Token**.

## Objetivo

Implementar autenticação com dois tokens:
- **Access Token**: válido por **1 hora**. Usado em todas as requisições autenticadas.
- **Refresh Token**: válido por **1 dia**. Usado exclusivamente para renovar o access token quando este expirar.

## Requisitos funcionais

### Backend (Spring Boot)

- Ao fazer login (`POST /api/auth/login`), o backend deve retornar:
  - `accessToken` (JWT, 1 hora).
  - `refreshToken` (JWT ou hash opaco, 1 dia).
  - Dados básicos do usuário (`id`, `nome`, `perfil`).

- Criar endpoint:
  - `POST /api/auth/refresh` → recebe o `refreshToken` e retorna um novo `accessToken`.

- O refresh token deve ser:
  - Único por usuário/sessão.
  - Armazenado de forma segura (hash) no banco.
  - Invalidado após uso ou ao expirar.
  - Revogado no logout.

- Ajustar o `JwtFilter` para rejeitar requisições com access token expirado, retornando status `401`.

### Banco de dados

- Criar migration Flyway `V4__refresh_tokens.sql` com tabela `refresh_tokens`:
  ```sql
  CREATE TABLE refresh_tokens (
    id BIGSERIAL PRIMARY KEY,
    usuario_id BIGINT NOT NULL,
    token_hash VARCHAR(255) NOT NULL UNIQUE,
    expiracao TIMESTAMP NOT NULL,
    utilizado BOOLEAN DEFAULT FALSE,
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_refresh_tokens_usuario FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
  );
  ```

### Frontend (Angular)

- Ajustar o modelo `LoginResponse` para receber `accessToken` e `refreshToken`.
- Armazenar ambos os tokens (localStorage ou em memória segura).
- Implementar interceptor que:
  - Adiciona o `accessToken` no header `Authorization`.
  - Detecta resposta `401` por token expirado.
  - Usa o `refreshToken` para chamar `POST /api/auth/refresh`.
  - Reenvia a requisição original com o novo access token.
  - Se o refresh falhar, redireciona para `/login`.
- Implementar lógica de renovação automática próxima da expiração (opcional).

### Segurança

- Nunca retornar o refresh token em texto claro após o login.
- O refresh token só pode ser usado no endpoint `/api/auth/refresh`.
- Revogar todos os refresh tokens ao alterar senha.

## Critérios de aceitação

- [ ] Login retorna access token (1h) e refresh token (1 dia).
- [ ] Access token expirado retorna 401 e é renovado automaticamente pelo frontend usando o refresh token.
- [ ] Refresh token expirado ou inválido redireciona o usuário para o login.
- [ ] Logout revoga/limpa o refresh token no backend e no frontend.
- [ ] Tabela de refresh tokens é criada via Flyway migration.
- [ ] Build do backend e frontend passam sem erros.
- [ ] Tokens não são logados em nenhum fluxo.

## Observações

- Manter compatibilidade com o design system Uber no frontend.
- Não hardcodar durações dos tokens; usar configuração em `application.yml` lendo do `.env`.
