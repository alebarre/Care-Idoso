## Contexto

Hoje o frontend foi construído com abordagem **mobile-first**, o que funciona bem em celulares em pé. Porém, ao aumentar a tela — seja celular deitado, tablet em pé/deitado ou desktop — os elementos (campos de texto, botões, cards, listas) se esticam horizontalmente ocupando toda a largura disponível, prejudicando a legibilidade, a estética e a usabilidade.

## Objetivo

Tornar o frontend **verdadeiramente responsivo**, respeitando o dispositivo **e** a orientação da tela, sempre dentro do padrão visual do app **Uber**.

## Breakpoints e comportamento esperado

| Dispositivo / Orientação | Largura aproximada | Comportamento esperado |
|--------------------------|--------------------|------------------------|
| Celular em pé            | < 480px           | Layout mobile atual: cards empilhados, botões e inputs full-width, padding confortável. |
| Celular deitado          | 480px – 767px      | Layout adaptado: container centralizado com largura máxima, menos esticamento, mantendo botões/inputs grandes. |
| Tablet em pé             | 768px – 1023px     | Layout tablet: grid de cards com 2 colunas, formulários em cards centralizados, melhor aproveitamento vertical. |
| Tablet deitado           | 1024px – 1365px    | Layout tablet horizontal: grid de 2-3 colunas, sidebar ou header expandido, maior densidade de informação. |
| Desktop                  | >= 1366px          | Layout desktop: sidebar de navegação fixa à esquerda, conteúdo centralizado em card principal, grids de 3-4 colunas. |

## Telas e componentes a serem ajustados

- **Login**: form não deve esticar além de ~400px no desktop; ficar centralizado vertical e horizontalmente.
- **Dashboard**: cards devem virar grid responsivo (1 coluna mobile, 2 colunas tablet, 3-4 colunas desktop).
- **Telas internas** (`idosos`, `rotinas`, `medicamentos`, `lembretes`, `pedidos`, `usuarios`):
  - Header fixo ou com layout adaptado.
  - Conteúdo em container centralizado com largura máxima.
  - Listas e cards respeitarem o breakpoint.
- **Formulários**:
  - Inputs e botões não devem exceder ~480px de largura no desktop (a menos que seja intencional, como tabelas).
  - Labels e campos devem ter alinhamento claro em telas maiores.
- **Botões**: manter altura mínima de 52px no mobile; no desktop podem ficar menores ou inline dependendo do contexto, mas sempre seguindo o padrão Uber (cantos arredondados, contraste forte).
- **Cards**: bordas arredondadas e sombras consistentes; no desktop usá-los como painéis agrupadores.

## Requisitos técnicos

- Usar media queries em `frontend/src/styles.scss` com base nos breakpoints acima.
- Criar/ajustar classes utilitárias como:
  - `.container` ou `.app-container` para limitar largura máxima.
  - `.grid-1`, `.grid-2`, `.grid-3`, `.grid-4` responsivos.
  - `.form-max` para limitar largura de formulários no desktop.
- Preferir **CSS Grid** e **Flexbox** para os layouts.
- Manter o design system Uber existente (variáveis CSS, cores, tipografia, botões e inputs).
- Garantir que as transições entre breakpoints sejam suaves, sem quebras visuais.

## Critérios de aceitação

- [ ] Login fica centralizado e não estica em telas grandes.
- [ ] Dashboard exibe cards em grid responsivo de acordo com o breakpoint.
- [ ] Telas internas possuem container com largura máxima coerente.
- [ ] Formulários mantêm legibilidade em todos os breakpoints.
- [ ] Layout em celular em pé permanece mobile-first.
- [ ] Layout em tablet em pé e deitado é distinto e aproveita o espaço extra.
- [ ] Layout em desktop possui aparência de aplicação desktop (não apenas mobile ampliado).
- [ ] Build do frontend passa sem erros.
- [ ] Não há scroll horizontal em nenhum breakpoint.

## Observações

- Seguir sempre o padrão visual do app Uber: tipografia Inter, alto contraste, botões arredondados, espaçamento limpo.
- Testar manualmente no Chrome DevTools com os presets: iPhone SE (em pé e deitado), iPad (em pé e deitado), Desktop.
